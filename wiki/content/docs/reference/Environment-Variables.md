---
title: Environment Variables
weight: 5
---

Every variable the tools and a running module read. All optional.

| Variable | Read by | Effect |
|---|---|---|
| `PWRS_PWSH` | `pwrs-build` (`pwsh.rs`) | the pwsh executable to run, instead of `pwsh` on `PATH` |
| `PWRS_PSHOME` | `pwrs-build` (`pwsh.rs`), `pwrs-host` (`lib.rs`) | `$PSHOME`, instead of running pwsh to print it; `pwrs-host` starts the runtime through the `hostfxr` under it, `pwrs_host::find_pshome` returns it before looking on PATH and refuses one that has no `pwsh.dll` and hostfxr, and `cargo pwrs toolchain` prints it |
| `PWRS_HOME` | `pwrs-build` (`toolchain.rs`) | the directory with `toolchain/` in it, instead of `~/.pwrs` (from `USERPROFILE` or `HOME`) |
| `PWRS_TOOLSET` | `pwrs-build` (`toolchain.rs`) | the `Microsoft.Net.Compilers.Toolset` version to fetch, instead of the pinned one. Each version gets its own tree under `toolchain/`, so switching neither refetches nor mixes two compilers under one lock |
| `PWRS_PESTER_PATH` | `cargo-pwrs` (`test.rs`) | a Pester module both hosts import, in place of the Pester 6.2.0 the toolchain fetches; with it set, nothing is fetched |
| `PWRS_PSGALLERY_KEY` | `publish.ps1` | the PowerShell Gallery API key; required unless `--dry-run` |
| `RUSTC` | `cargo-pwrs` (`cpu.rs`) | the compiler `cargo pwrs build` runs as `rustc --print cfg`, with `--target` for a cross build, to read which extensions the target enables by default, so it can warn about a library compiled for more; `rustc` on `PATH` otherwise, as cargo does |
| `PWRS_MODULE` | your Pester tests | set by `pester.ps1` to the built module folder |
| `PWRS_SURFACE_DIR` | a running module (`surface.rs`), set by `cargo pwrs test` | the directory each native image in each process writes `<pid>-<image>.tsv` to, so two PWRS modules in one process write separate files, recording per cmdlet how many phases ran, how many called `should_process` or `should_continue`, and which parameters took a value from the pipeline. Unset, which is every production call, a phase pays one relaxed load and a branch. `cargo pwrs test` sets it, clears the directory first, and reads what both hosts leave |
| `PWRS_THREAD_CHECK` | a running module (`host.rs`), set by `cargo pwrs test` | `1` makes a `PsObject` method called from a thread the host did not call the module on (a worker the module started) return an error with id `PwrsOffThread` instead of running, unless the thread has the guard `pwrs::attach_current_thread()` returns. A debug build checks whatever it says; a release build checks only when it is `1` |
| `PWRS_CPU_MAX` | a running module (`cpu.rs`, `CpuCheck.cs`) | caps the x86-64 extensions a module may use at one psABI level: `x86-64`, `x86-64-v2`, `x86-64-v3` or `x86-64-v4`, with `native` or unset for no cap. `pwrs::cpu::has` applies the cap, and the import check refuses a library compiled for more than it allows, so one machine can run every tier of a module. Any other value refuses the import |
| `PWRS_TRACE` | a running module (`trace.rs`, `Native.cs`), and `cargo-pwrs` through `pwrs-build` (`trace.rs`) | in a module, `1` prints the Rust side's counters to stderr every 10000 instance creations and the managed side's every 10000 phases; `2` prints every event on the Rust side; unset or `0` prints nothing and skips the counter sites. Has to be in the environment the process inherits: assigning it inside PowerShell through `$env:` was observed on Linux to reach the managed counters only. In `cargo pwrs`, any value but empty or `0` prints a line to stderr when each process it starts begins, with its pid, command line and the variables set for it, and one when it ends, with how long it ran and its status; see [How To Trace A Module](../how-to/How-To-Trace-A-Module.md) |

Others are read as well, none of them a setting of PWRS's own. `USERPROFILE` or `HOME` places `~/.pwrs`, where the toolchain is stored unless `PWRS_HOME` names another folder, and the copy `pwrs-host` makes of a Store install's `$PSHOME` under `pshome/`. `PATH` is where `pwrs_host::find_pshome` looks for pwsh, and on Windows a library that fails to load is described against the folders it names as well as the system's. `ProgramFiles` places PowerShell 7's default install folder on Windows for `find_pshome`. `CARGO_HOME`, or `.cargo` in the home folder when it is unset, places the files a `native-files` entry downloads, under `pwrs/downloads`. `PSModulePath` is passed to a Windows PowerShell run with PowerShell 7's module directories taken out. `CLR_ICU_VERSION_OVERRIDE` is set by `pwrs-host`, when the pwsh it hosts is a Linux snap, to the version of the ICU the snap has, unless it is already set. On Linux, macOS and FreeBSD, `XDG_CACHE_HOME` is set for each pwsh `cargo pwrs` runs for a step of its own (the toolchain fetch, a C# compile, the `$PSHOME` query) to a new folder under the temporary folder, removed when that pwsh ends. So that pwsh neither reads nor writes the startup profile other pwsh processes write in `~/.cache/powershell`, which pwsh processes ending at once can leave corrupt for every pwsh started after ([PowerShell/PowerShell#26528](https://github.com/PowerShell/PowerShell/issues/26528)). Pester under `cargo pwrs test` and `publish.ps1` run in the environment `cargo pwrs` was given. Nothing else is read from the environment. The toolchain fetch uses `Invoke-WebRequest`, which honors the host's proxy settings.
